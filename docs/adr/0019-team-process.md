# ADR-0019: Командный процесс — Issues, доска, ревью

Статус: принято · 2026-11-27 · частично заменяет [ADR-0010](0010-git-process.md) (одобрения)

## Контекст

ADR-0010 и ADR-0011 писались, когда почти всю работу делал один человек: «одобрения не требуются», proposal шёл отдельным PR. Теперь задачи делят 4 человека без жёстких ролей. Доски задач нет, и не видно, кто что взял: уже появились две ветки на одну работу. Обязательный approve в ruleset `master` уже включён в GitHub, а документы говорят обратное.

## Решение

1. **Задачи хранятся в GitHub Issues и на доске GitHub Projects.** Колонки: Backlog → In progress → In review → Done.
2. **Один issue = одно изменение OpenSpec = одна ветка = один PR.** Строки `tasks.md` в issue не дублируются. Если работа велика для одного человека, её делят на несколько изменений OpenSpec.
3. **Колонки остаются как есть, четыре штуки.** Задача проходит доску один раз: proposal и код лежат в одной ветке и уходят одним PR.
4. **Proposal утверждает автор задачи своему агенту,** до кода и без PR. **PR целиком утверждает любой член команды, кроме автора:** approve на PR. PR без approve не сливается (ruleset `master`).
5. **Сливает автор,** когда есть approve и зелёный CI. Архив OpenSpec кладётся последним коммитом. В тексте PR пишется `Closes #N`.
6. **Задачу берут через Assignee:** ставят себя исполнителем, переводят карточку в In progress, потом создают ветку. Задачу с исполнителем не трогают, а пишут исполнителю. Ролей и лимита задач нет.
7. **Метки:** по пакету (`core`, `frontend`, `backend`, `shared`, `e2e`, `ci`, `docs`) и по типу (`feat`, `fix`, `chore`). Сроков и вех (milestones) нет.

Правила для людей собраны в [`CONTRIBUTING.md`](../../CONTRIBUTING.md). Issues и метки заводит человек: агент GitHub не трогает (ADR-0011).

## Варианты

- **Trello или Notion.** Привычно, но лежит отдельно от кода и не связано с PR.
- **Только OpenSpec.** Ничего нового заводить не нужно, но не видно, кто что взял.
- **Sub-issues на блоки `tasks.md` или issue на каждую строку.** Задачи пришлось бы вести в двух местах, а доска зарастает.
- **Колонка Ready или метки `proposal` / `code`.** Этап виден лучше, но команда выбрала не менять доску.
- **Отдельный PR для proposal, его утверждает команда.** Так делали раньше (`docs/propose-...`). Но тогда на одну задачу два PR, карточка дважды ходит по доске, а `Closes #N` в первом PR закрыл бы задачу до кода.
- **Утверждает только лидер.** Архитектурой владеет один человек, но он становится узким местом.
- **Сливает ревьюер или один выделенный человек.** Ветки ждут чужих рук, а автор не доводит задачу до конца.

## Последствия

- Без второго человека PR не сольёшь. Ревью и approve видны в истории GitHub и на защите.
- Если в ruleset включено «dismiss stale approvals», коммит с архивом сбрасывает approve. Ревьюер ставит его заново: в этом коммите меняется только `openspec/`.
- Агент перед работой спрашивает номер issue и предлагает `Closes #N` в тексте PR.
