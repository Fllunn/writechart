# Design

## Context

Процесс сейчас записан в четырёх местах: ADR-0010 (git), ADR-0011 (OpenSpec и агенты), `AGENTS.md` («Как работаем», «Процесс»), `docs/architecture.md` (раздел про процесс). Все они написаны под одного человека. Обязательный approve в ruleset `master` уже включён в GitHub, а документы говорят обратное. Доска GitHub Projects с колонками Backlog / In progress / In review / Done у команды уже есть. `gh` на машине нет, поэтому агент GitHub не трогает (ADR-0011, ADR-0013).

## Goals / Non-Goals

**Goals:**
- Одно место с правилами для людей: `CONTRIBUTING.md`.
- Одно решение с причинами: ADR-0019. ADR-0010 не переписывается, только получает пометку о замене (правило `docs/adr/README.md`).
- Агенты знают про issue и `Closes #N`.

**Non-Goals:**
- Автоматизация доски (GitHub Actions, которые двигают карточки). Projects и так сам переводит закрытый issue в Done.
- Проверка, что в PR есть `Closes #N` (как с commitlint: правило без автопроверки).

## Decisions

1. **Задачи хранятся в GitHub Issues + Projects.** Это бесплатно, лежит рядом с кодом, `Closes #N` сам закрывает issue, вклад виден на защите. Отвергнуты: Trello и Notion (не связаны с кодом и PR) и вариант «только OpenSpec» (не видно, кто что взял).
2. **Один issue = одно изменение OpenSpec.** Строки `tasks.md` в issue не дублируются. Если работа велика для одного человека, её делят на несколько изменений OpenSpec, а не на sub-issues. Отвергнуты: sub-issues на блоки `tasks.md` и issue на каждую строку (доска зарастает).
3. **Колонки остаются как есть, четыре штуки.** Задача проходит доску один раз: proposal и код в одной ветке, один PR. Отвергнуты: колонка Ready и метки `proposal`/`code`.
4. **Proposal утверждает автор задачи своему агенту, PR целиком утверждает любой не автор.** Отвергнуты: отдельный PR для proposal с approve команды (два PR на задачу, `Closes #N` в первом закрыл бы задачу до кода), «только лидер» (узкое место) и смешанный вариант (лидер утверждает архитектурные изменения). «только лидер» (узкое место) и смешанный вариант (лидер утверждает архитектурные изменения).
5. **Сливает автор** после approve и зелёного CI. Он же последним коммитом кладёт архив OpenSpec. Отвергнуты: «сливает ревьюер» и «сливает один выделенный человек».
6. **Берут задачу через Assignee.** Сначала Assignee и In progress, потом ветка. Лимита нет: команда отказалась.
7. **Метки по пакету и по типу.** Без `architecture` и `good first issue`.
8. **Шаблон issue — форма `task.yml`** с полями «Что сделать», «Пакеты» (флажки), «Изменение OpenSpec» (необязательно, пока proposal нет). Метки форма не ставит: по выбору в форме GitHub их не назначает, так что метки ставит человек.

## Risks / Trade-offs

- [Задача ездит туда-обратно по колонкам, легко забыть её передвинуть] → в `CONTRIBUTING.md` таблица «этап → колонка».
- [Approve обязателен, без второго человека PR не сольёшь] → это и есть цель. В `CONTRIBUTING.md` написано: нужен ревьюер — попроси в чате команды.
- [Новый коммит после approve может сбросить approve, если в ruleset включено «dismiss stale approvals»] → коммит с архивом меняет только `openspec/`, ревьюер быстро ставит approve повторно. Это записано в `CONTRIBUTING.md`.
